# 一个能被 AI 维护的第二大脑：设计与取舍

> 这篇文章说明**为什么这样设计**，不展开操作步骤。配套的规则文本、可用命令与空白模板都在本仓库里。
> 适合读者：已经用 Obsidian 记东西，但觉得「存了很多、用不上、还得自己管」的人。

## 一、要解决的不是「存不下」，是三个失败模式

个人知识库通常不是没东西，而是三种失败同时发生：

| 失败模式 | 表现 | 常见误判 |
|---|---|---|
| **归档不消化** | 材料按日期越堆越多，但没有一条可复用的理解 | 以为「存进去」等于「记住了」 |
| **规则是散文** | 规则写得很细，没有任何东西能证明它被执行过 | 以为「写了规则」等于「规则生效」 |
| **入口成本膨胀** | 每次开工都要先读几千行目录，越用越慢 | 以为「越全」等于「越好用」 |

三者互相喂养：入口越贵，越不敢开工；越不开工，材料越不消化；越不消化，就越想再写更多规则来自救，入口再涨一轮。

整套设计只做一件事：**给这三条各划一条硬边界**。

## 二、四条设计原则

### 2.1 原始层不可变，派生层可再生

`raw/` 是证据，只读、不改写、不为整洁而移动。`wiki/` 是从它派生的理解层，理论上可以整层删掉再重建。

价值不在整洁，在**爆炸半径**：模型错了，坏的是可再生的派生层；只要原始层没被碰过，一次重跑就能清掉。反过来，一旦允许模型改原始层，一次幻觉就是永久的证据污染。

### 2.2 规则必须落成命令

能被机器判定的规则，都要有一个可执行命令，退出码即结论。

散文规则的问题不是写得不好，是**无法被证伪**。「重要结论能追溯」这句话在散文里永远成立——直到真的去查，才发现两百多条溯源路径全是断的，而且一直没人发现。

命令化买到三件事：任何助手跑同一条命令得同一定论；人不必重读规则就能验收；规则改坏了，工具立刻报错。

### 2.3 判断不能外包

记录可以自动，判断不行。

模型很擅长写出「看起来合理」的关系，但很难可靠区分「看起来合理」和「半年后仍然站得住」。所以分工是：**来源之间何处一致、何处冲突，可以从材料客观归纳；「我自己的判断」必须由本人写**。助手能做的是把候选摆好、把冲突标出来、把证据缺口标出来，然后把结论的位置留空。

### 2.4 确认门按「能不能撤销」分级

一律要确认，等于把管理成本转回给人；一律不要确认，等于把正确性押在模型上。

分级依据不是「重不重要」，而是**「错了能不能撤销」**：

| 撤销成本 | 动作 | 授权 |
|---|---|---|
| 可撤销 | 追加记录、建来源页、更新索引 | 直接做，事后报告 |
| 部分可撤销 | 改旧文、合并页面、移动文件 | 直接做，进待决清单 |
| 不可撤销 | 删除、对外发布、写长期画像 | 先问 |

## 三、结构：四层 + 两个支撑层

| 层 | 目录 | 装什么 | 谁写 |
|---|---|---|---|
| 证据层 | `raw/`、`Clippings/` | 外部原始材料 | 人；助手只读 |
| 个人记录层 | `diary/` | 日记、情绪、自我记录 | 人主写；助手按授权追加 |
| 知识层 | `wiki/` | 来源、实体、概念、对比、主题入口 | 助手提议 |
| 输出层 | `work/` | 简历、文章、方案、任务档案 | 协作 |
| 工具层 | `tools/` | 把规则变成命令 | 协作维护 |
| 草稿层 | `wiki/草稿/` | 自己尚未成熟的想法，不设阈值 | 人 |

草稿层最容易被忽略，也最必要。前四层各司其职，但没有一层容纳「我觉得有点意思，但还站不住」的东西。缺了它，人只有两个选择：提前升格成知识页（制造噪音），或者根本不记（丢失）。

## 四、入口要做成地图，不是目录

索引有两种做法：把所有条目平铺，或者只放主题入口。

平铺在几百条以内确实好用——检索不用多跳。但它有个隐藏成本：**每次开工都要先付一次全量浏览的钱**，而这个成本随摄入线性增长。

地图做法是：入口只放主题入口页与统计，全量清单另存一层；约束是每个知识页从入口**一跳可达**，而不是全部列在入口。

这和「不要把一切塞进一个巨型指令文件」是同一个教训：上下文是稀缺资源，巨型入口会挤掉任务本身的信息。

## 五、把「想记」和「整理」拆开

大多数知识库死于一个摩擦点：想起来的时候不在电脑前，在电脑前的时候想不起来。

拆开之后，通道只负责两件事：**投递**（在任何设备上把东西丢进去，不需要组织语言）和**回执**（告诉你收到了、放哪了、哪些要你拍板）。整理不发生在投递那一刻，而发生在后台。

### 5.1 通道的三个约束

- **不依赖公网入口**：长连接从本机主动连出去，不需要公网 IP、不需要备案域名。
- **允许延迟**：本机不一定常开。消息留在服务端，开机后按消息 ID 补跑并去重。
- **回执不含原文**：外部通道只回结构信息（几条、落在哪），可读内容留在库内。外部通道是别人的服务器，这条边界是设计的一部分，不是事后补丁。

### 5.2 意图要落成协议，不是交给模型猜

一句「把最近的截图收一下」，应该被展开成一个**确定的动作集合**：时间范围、候选清单、目标目录、跳过规则。

展开由固定规则完成。理由是**可复现**：同一句话在任何一天执行，得到同一个候选清单；出错能定位到规则，而不是「模型那天心情不同」。

模型只在协议的**填空处**工作：这段内容讲什么、该归哪个主题、一句话简介怎么写。超出协议范围的部分，才回退给通用助手自由处理。

## 六、自动化边界

这张表就是整套设计的核心：

| 动作 | 谁做 | 为什么 |
|---|---|---|
| 归档新材料、生成来源页 | 自动 | 事实性工作，可验证、可回滚 |
| 更新统计、索引、日志 | 自动 | 同上 |
| 检查断链、阈值、隐私、空壳 | 自动 | 判定规则明确，不需要理解内容 |
| 归纳「哪些来源一致、哪些冲突」 | 自动 | 可核对，能回指具体来源 |
| 判断「这个值不值得立概念页」 | **人** | 需要长期检索价值的取舍 |
| 判断「旧结论要不要改」 | **人** | 涉及自己认识的演变，不能静默覆盖 |
| 更新长期画像 | **人** | 关系到「我是谁」的表述 |
| 删除、合并、移动 | **人** | 不可撤销 |

自动的部分必须能自证（跑命令、看退出码）；留人的部分必须**便宜**——一次一句话、一周看一眼，否则它就会退化成第二个收件箱。

## 七、已知代价

诚实列出，避免按最优情况预期：

1. **起步成本不会归零**：规则、契约、入口加起来仍要几千 token。收益是它不再随摄入增长。
2. **自动整理会引入噪音**：分类错误、重复页面、来源不独立都会发生。缓解靠定期检查，不是靠一次做对。
3. **判断清单会积压**：这是设计的一部分，不是失败。积压说明该看一眼，而不是该扩大自动化。
4. **多模态有硬边界**：图片 OCR 可以本地做；语音转写在没有免费本地方案时只能靠系统听写；各平台的对话导出格式不统一，只有部分平台有官方导出。
5. **外部通道会留副本**：凡进通道的内容，都按「已经离开本机」对待。

## 八、不适合谁

- 想要「一键生成知识库」的人：它需要持续投入，只是把投入从「整理」挪到了「看一眼清单」。
- 不愿意保留原始层的人：没有不可变证据，派生层就只是二手转述。
- 需要多人共享编辑的人：这里的确认门和隐私分级是单人设计。

## 九、本仓库提供什么

| 文件 | 作用 |
|---|---|
| `tools/memory.py` | 对话导入、主题页生成、接续说明、去重与审计 |
| `tools/intent.py` | 一句中文指令 → 确定的动作计划（时间窗、候选、落点、跳过规则） |
| `tools/worker.py` | 收件箱 → 归档 → 来源页 → 更新档案页/索引/日志 → 自检；含月度费用上限 |
| `tools/brief.py` | 每日简报（库内版与外部通道版两套，后者不含原文） |
| `vault/AGENTS.md` | 跨助手操作契约：先跑协议、回执不引原文、判断留清单 |
| `tests/` | 全部命令的固定用例，26 项 |

设计上没有「必须用某个模型」的依赖：协议与检查都是纯规则，模型只负责摘要和主题归类；换一个兼容 OpenAI 接口的国内模型，改两个环境变量即可。
